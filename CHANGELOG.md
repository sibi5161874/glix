## [Unreleased]

### Added (Phase 7 — Reports)
- `/reports` hub with cards linking to 4 reports, and a shared `ReportsSubnav` tying them together: `/reports/employees` (demographics by department, designation, gender, employment type, status), `/reports/leaves` (allocated vs. used by leave type for a selectable year, pending requests, approved days), `/reports/documents` (expiry summary + breakdown by document type), `/reports/loans` (outstanding/repaid summary + breakdown by status). All four gated to `org_admin`/`org_staff` (`reports:read`), matching every other feature's RBAC pattern — `org_viewer` sees a permission message, enforced server-side regardless of the UI.
- CSV, Excel (`.xlsx`), and PDF export on every report via a shared `ReportExportButton` dropdown, downloading through the browser's blob/`<a download>` pattern already established in `/employees/import-export`. Backend: `backend/src/services/report-export.service.ts` provides generic `buildCsv`/`buildXlsx`/`buildPdf` builders shared across all 4 reports; new `pdfkit` dependency (pure JS, no native bindings — documented in `.agents/rules/backend-constitution.md`).
- Backend: `report.repository.ts` (demographics/leave-utilization/document-type/loan-status aggregation queries), 4 per-domain services, `report.controller.ts`, and `GET /v1/reports/{employees,leaves,documents,loans}` + `/export` routes, all server-side filtered and permission-guarded (`reports:read`, `reports:export`). 11 new integration tests (89 total across monorepo) covering role gates, each report's data shape, and all 3 export formats' content-type headers.

### Fixed (Phase 7)
- **`pg` concurrent-query deprecation** — `employeeDemographics` (5 breakdowns), the documents report, and the loans report each ran multiple `client.query()` calls via `Promise.all` on the *same* tenant-scoped `PoolClient` inside one `withTenant` transaction. A single `pg` connection can't have two queries in flight at once; `pg` currently queues them and logs "Calling client.query() when the client is already executing a query is deprecated and will be removed in pg@9.0." Caught from that warning appearing in the new test run, before it shipped. Fixed by converting all three to sequential `await`s; confirmed via `grep -rn "Promise.all" backend/src/services backend/src/repositories` that no other repository/service has the same pattern.

### Added (audit-fix pass — CI, security, tests)
- **CI now has a real database.** `.github/workflows/ci.yml` had no Postgres service at all — `pnpm test` was guaranteed to fail on every PR the moment any backend test existed (it did, from this project's own first backend tests). Added a `postgres:16` service container, `DATABASE_URL`/`DATABASE_URL_MIGRATE`/`JWT_SECRET` env, and `db:migrate`/`db:seed` steps before `pnpm test`. Also added a second `e2e` job: its own Postgres service, backend started in the background, `wait-on` for its health check, then `pnpm --filter frontend test:e2e` against a production build.
- **`auth.routes.test.ts`** (12 tests): register (happy path, validation, duplicate-slug 409), login (email+password, employee-code+DOB, wrong password vs. nonexistent email returning the *identical* message — the actual anti-enumeration property, not just "doesn't contain the word 'password'"), `/me`, and rate-limit enforcement. `auth.service.ts` — the highest-risk code in the app — had zero tests before this.
- **Rate limiting** (`@fastify/rate-limit`, registered `global: false`, opt-in per route) on `/v1/auth/login` (10/min) and `/v1/auth/register` (5/min) — previously completely unmitigated.
- **A real Playwright E2E suite** (`frontend/e2e/`, `frontend/playwright.config.ts`): login → create employee → appears in list → delete, with an `afterEach` API-level cleanup hook so a failed run can't leave data behind. `test:e2e` was referenced in root `package.json` but the script didn't exist in `frontend/package.json` at all — fixed by actually building the suite the audit asked for, not just adding a script.
- **Structured error logging and crash guards** — no external APM (Sentry or equivalent) is wired in and this doesn't pretend otherwise (see `backend-constitution.md` §8 for the honest version), but `sendError` now attaches `orgId`/`userId`/`method`/`url` to every unhandled-error log line (it previously discarded `req` entirely), and `index.ts` gained `uncaughtException`/`unhandledRejection` handlers so a crash is never silent.
- **Tier-limit enforcement extracted and reused:** `tier-limit.service.ts` generalizes what was employee-only logic; Documents' storage limit (`tiers.config.ts`'s `maxStorageMb`) had no backing check anywhere until now — upload a file and it's enforced server-side like every other tier limit.
- **`/v1` API versioning contract documented** (`ARCHITECTURE.md` §7) — what counts as breaking, how a `/v2` would be introduced, the deprecation window, and an explicit callback to this session's own dashboard-crash bug as an example of contract drift that versioning alone doesn't prevent.

### Fixed (audit-fix pass)
- **CSP was disabled outright** (`contentSecurityPolicy: false` in `backend/src/app.ts`) rather than tuned. Re-enabled with `default-src 'none'` — correct for an API that never renders HTML.
- **5 dependency CVEs** (2 high, 3 moderate — `postcss` via `next`'s bundled copy, `uuid` via `exceljs`), all transitive. Cleared via `pnpm.overrides` in root `package.json` rather than waiting on upstream.
- **`sendError` dropped plugin-thrown errors that had a `statusCode` but no `code`** (discovered via the new rate-limit test: `@fastify/rate-limit`'s 429 has no `code` field) — fell through to a generic 500 instead of the real 429. Relaxed the type guard to only require `statusCode` + `message`.
- **The employees list's pagination `total` would have silently misreported as 0** for a window-function count optimization (`employee.repository.ts`) whenever `page` landed past the last page (e.g. after deleting the last row on that page) — a page with zero rows has no row left to carry the total on. Added a fallback count query for that one case, and a regression test. Caught during code review of my own optimization, before it shipped.
- **3 icon-only action buttons had no accessible name** (`employee-row-actions.tsx`, `loan-row.tsx`, `announcement-card.tsx` — all a bare `<MoreHorizontal />` with nothing else), found while wiring Playwright selectors for the new E2E test. Added `aria-label`.
- `docs/BUILD_PLAN.md`'s checklist was unticked for Phases 1-4 despite being complete (only Phases 5-6 had been ticked) — now reflects reality through Phase 6.
- `/employees/import-export`'s export always downloaded every employee regardless of the list page's active filters. Now forwards `search`/`departmentId`/`status` through the page link and into the export request, with the UI copy reflecting whether filters are active.

### Fixed (found during post-hoc verification of Phases 4-6, before first commit)
- **Dashboard crash:** `/dashboard` threw `TypeError: announcements.map is not a function` on every load. `announcementService.list` returns the same paginated `{ items, total, page, limit }` envelope as Employees/Documents/Loans, but `frontend/src/lib/announcements.ts`'s `listAnnouncements` was typed as returning a bare `AnnouncementItem[]` and all three call sites (`dashboard/page.tsx`, `announcements/page.tsx`, `announcements-table.tsx`) treated it as one. Fixed by returning the full envelope (matching `listDocuments`/`listLoans`'s established pattern) and unwrapping `.items` at each call site.
- **Date-shift bug (Documents):** `issue_date`/`expiry_date` are `date` columns; node-pg parses them as a JS `Date` at *local* midnight, and the mapper's `.toISOString().split("T")[0]` shifted the date backward by one day in any positive-UTC-offset timezone (reproduced in dev under IST — `2026-01-01` round-tripped as `2025-12-31`). Fixed by casting both columns to text in SQL (`to_char(..., 'YYYY-MM-DD')`) instead of relying on JS Date parsing; extracted the mapper into `document-mapper.ts` (`document.repository.ts` was also 295 lines, over `RULES.md` §3's 250-line cap). Added a regression test asserting exact round-trip.
- **Date-shift bug (Loans), same root cause:** `loans.start_month` had the identical bug — a loan's start date silently displayed one day earlier than entered (browser-reproduced: entered `2026-11-01`, UI showed `2026-10-31`). Fixed the same way (`to_char` cast in `loan.repository.ts`); added a regression test.
- **Test-data leak:** `documents.routes.test.ts` created a "Security Clearance" document type on every run with no cleanup (only its generated `code` was unique) — 11 duplicate rows had accumulated in the dev DB, visible in the document-type filter dropdown. Added `afterAll` cleanup, same pattern as `leave-workflow.routes.test.ts` hit earlier this session.
- **File-size violations (`RULES.md` §3, 250-line cap):** `document.repository.ts` (295 lines), `documents-table.tsx` (336), `loans-table.tsx` (355), and `announcements-table.tsx` (266) all exceeded the limit. Split each into focused sub-components (`document-mapper.ts`; `document-summary-cards.tsx` + `document-row.tsx`; `loan-summary-cards.tsx` + `loan-row.tsx`; `announcement-card.tsx`) with no behavior change.

### Fixed
- `frontend/src/lib/api.ts`'s `apiFetch` sent `Content-Type: application/json` on every request, including bodyless ones (e.g. `DELETE /v1/employees/:id`). Fastify's JSON parser rejects an empty body under that header, which the client surfaced as a generic failure. Fixed by only setting the header when a body is present.
- `backend/src/utils/http.ts`'s `sendError` treated any non-`AppError` — including Fastify's own request-parsing errors (bad/empty JSON body, unsupported content-type), which carry a real client-facing `statusCode` — as an opaque 500. Now a Fastify `FST_ERR_*`-style 4xx error is reported as the 4xx it is.
- The employee create/edit form's `basicSalary` number input submitted as a string against the `z.number()` schema (`<Input type="number">` spread via RHF's `{...field}` doesn't coerce). Fixed with an explicit `Number(e.target.value)` conversion.
- In create mode, the form's `status` field defaulted to a `status: undefined` key that's absent from `CreateEmployeeInput`'s shape entirely (it only exists on `UpdateEmployeeInput`). `.strict()` rejects an unrecognized key even when its value is `undefined`, since RHF still submits the key — this silently blocked every employee creation with no visible error. Fixed by omitting the key entirely from `defaultValues` in create mode.

### Security
- Env validation via Zod at runtime boundaries (`shared/config/env.ts`).
- Enforced PostgreSQL Row Level Security (RLS) across all tenant tables and private storage buckets.
- Append-only `audit_log` with database trigger blocking updates and deletes.
- **Fixed — RLS table-owner bypass.** `glix_user` (table owner, ran migrations) was also the backend's runtime DB role; PostgreSQL exempts owners from their own RLS policies, so RLS provided no actual tenant isolation — verified empirically (a bogus `app.org_id` still returned every row). Fixed via migration `020_roles.sql`: `glix_app`, a non-owner role with only row-level DML grants, is now the backend's runtime role (`DATABASE_URL`); `glix_user` is kept as the migrations/seed-only role (`DATABASE_URL_MIGRATE`). Migration `019_users_insert_policy.sql` also added the `INSERT` policy `006_rls_policies.sql` was missing for `users`, plus a `SECURITY DEFINER` `create_user()` function for the signup path. `pnpm verify:rls` (`scripts/verify-rls.ts`) now proves cross-tenant isolation empirically — two fixture orgs' employees are confirmed mutually invisible under `glix_app`. See `SECURITY.md` §2 and `ARCHITECTURE.md` §5.
