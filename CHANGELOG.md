## [Unreleased]

### Fixed (found during post-hoc verification of Phases 4-6, before first commit)
- **Dashboard crash:** `/dashboard` threw `TypeError: announcements.map is not a function` on every load. `announcementService.list` returns the same paginated `{ items, total, page, limit }` envelope as Employees/Documents/Loans, but `frontend/src/lib/announcements.ts`'s `listAnnouncements` was typed as returning a bare `AnnouncementItem[]` and all three call sites (`dashboard/page.tsx`, `announcements/page.tsx`, `announcements-table.tsx`) treated it as one. Fixed by returning the full envelope (matching `listDocuments`/`listLoans`'s established pattern) and unwrapping `.items` at each call site.
- **Date-shift bug (Documents):** `issue_date`/`expiry_date` are `date` columns; node-pg parses them as a JS `Date` at *local* midnight, and the mapper's `.toISOString().split("T")[0]` shifted the date backward by one day in any positive-UTC-offset timezone (reproduced in dev under IST — `2026-01-01` round-tripped as `2025-12-31`). Fixed by casting both columns to text in SQL (`to_char(..., 'YYYY-MM-DD')`) instead of relying on JS Date parsing; extracted the mapper into `document-mapper.ts` (`document.repository.ts` was also 295 lines, over `RULES.md` §3's 250-line cap). Added a regression test asserting exact round-trip.
- **Date-shift bug (Loans), same root cause:** `loans.start_month` had the identical bug — a loan's start date silently displayed one day earlier than entered (browser-reproduced: entered `2026-11-01`, UI showed `2026-10-31`). Fixed the same way (`to_char` cast in `loan.repository.ts`); added a regression test.
- **Test-data leak:** `documents.routes.test.ts` created a "Security Clearance" document type on every run with no cleanup (only its generated `code` was unique) — 11 duplicate rows had accumulated in the dev DB, visible in the document-type filter dropdown. Added `afterAll` cleanup, same pattern as `leave-workflow.routes.test.ts` hit earlier this session.
- **File-size violations (`RULES.md` §3, 250-line cap):** `document.repository.ts` (295 lines), `documents-table.tsx` (336), `loans-table.tsx` (355), and `announcements-table.tsx` (266) all exceeded the limit. Split each into focused sub-components (`document-mapper.ts`; `document-summary-cards.tsx` + `document-row.tsx`; `loan-summary-cards.tsx` + `loan-row.tsx`; `announcement-card.tsx`) with no behavior change.

### Fixed
- `frontend/src/lib/api.ts`'s `apiFetch` sent `Content-Type: application/json` on every request, including bodyless ones (e.g. `DELETE /v1/employees/:id`). Fastify's JSON parser rejects an empty body under that header, which the client surfaced as a generic failure. Fixed by only setting the header when a body is present.
- `backend/src/utils/http.ts`'s `sendError` treated any non-`AppError` — including Fastify's own request-parsing errors (bad/empty JSON body, unsupported content-type), which carry a real client-facing `statusCode` — as an opaque 500. Now a Fastify `FST_ERR_*`-style 4xx error is reported as the 4xx it is.
- The employee create/edit form's `basicSalary` number input submitted as a string against the `z.number()` schema (`<Input type="number">` spread via RHF's `{...field}` doesn't coerce). Fixed with an explicit `Number(e.target.value)` conversion.
- In create mode, the form's `status` field defaulted to a `status: undefined` key that's absent from `CreateEmployeeInput`'s shape entirely (it only exists on `UpdateEmployeeInput`). `.strict()` rejects an unrecognized key even when its value is `undefined`, since RHF still submits the key — this silently blocked every employee creation with no visible error. Fixed by omitting the key entirely from `defaultValues` in create mode.

### Security
- Env validation via Zod at runtime boundaries (`shared/config/env.ts`).
- Enforced PostgreSQL Row Level Security (RLS) across all tenant tables and private storage buckets.
- Append-only `audit_log` with database trigger blocking updates and deletes.
- **Fixed — RLS table-owner bypass.** `glix_user` (table owner, ran migrations) was also the backend's runtime DB role; PostgreSQL exempts owners from their own RLS policies, so RLS provided no actual tenant isolation — verified empirically (a bogus `app.org_id` still returned every row). Fixed via migration `020_roles.sql`: `glix_app`, a non-owner role with only row-level DML grants, is now the backend's runtime role (`DATABASE_URL`); `glix_user` is kept as the migrations/seed-only role (`DATABASE_URL_MIGRATE`). Migration `019_users_insert_policy.sql` also added the `INSERT` policy `006_rls_policies.sql` was missing for `users`, plus a `SECURITY DEFINER` `create_user()` function for the signup path. `pnpm verify:rls` (`scripts/verify-rls.ts`) now proves cross-tenant isolation empirically — two fixture orgs' employees are confirmed mutually invisible under `glix_app`. See `SECURITY.md` §2 and `ARCHITECTURE.md` §5.
